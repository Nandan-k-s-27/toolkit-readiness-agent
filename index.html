🛡️ Extra Verification Loop: Client-Side SPA / Headless Browser Detection
Standard HTTP fetch fails silently on Single Page Applications (SPAs) where client-side JavaScript dynamically loads documentation. Our agent runs an explicit DOM skeleton detector for markers such as <div id="root">, <div id="app">, or "enable javascript to run this app".
What it caught: On Paygent Connect and higgsfield, client-side React/Vue shells hid documentation from naive scrapers. Rather than allowing the LLM to hallucinate synthetic endpoints, the loop flagged them immediately and routed them to human_queue.json for manual audit.

✅ Highest Accuracy Fields
• Buildability (70.0%): Strong signal on whether an API exists and can be integrated into an AI agent toolkit.
• Access Model (60.0%): High reliability identifying self-serve developer access vs paid/approval gated tiers.
⚠️ Challenging Fields
• Existing MCP (30.0%): Model Context Protocol servers are newly emerging weekly; official vs community tagging shifts rapidly.
• Auth Protocols (16.7%): Strict exact multi-label set match penalizes returning bearer_token vs api_key synonyms.
🛑 Difficult Cases That Defeated the Agent
• Paygent Connect & Waterfall.io: Enterprise sales walls completely withhold public documentation.
• Plaid: Sandbox is self-serve, but live production credentials require compliance underwriting approval.
• Ahrefs & Otter AI: Consumer UI accounts exist, but developer API requires bespoke enterprise contracts.
• Twilio: Complex dual scheme (HTTP Basic Account SID/Token + HMAC webhook signing).
